Platform Architecture

UnicAthlete Ecosystem

Platform-level decisions for the MVP and the architecture choices we want to preserve for later scaling.

MVP Platform Scope

The MVP focuses on the athlete showcase and the recruiter/scout workflow. The model stays open for additional profile and professional types later.

MVP Profile Types

The platform starts with two profile types only: Athlete Profile and Professional Profile.

  • Athlete Profile is the athlete-facing public showcase.
  • Professional Profile is the private operating identity for professionals.
Athlete Professional
Future scaling plans: add Fan Profile, Coach Profile, Guardian-facing profile surfaces, or other role-specific profiles without changing the base User model.

MVP Professional Type

For the MVP, the Professional Profile supports one active professional type: Recruiter / Scout.

  • Recruiter / Scout gets the first professional workflow.
  • Scout Profile stores identity, affiliation, expertise, and professional context.
  • Scout activity summaries live in the dashboard, not as a public portfolio.
Recruiter Scout
Future scaling plans: add nutritionists, physicians, physiotherapists, agents, coaches, and other professional categories as additional professional_type values.

User And Profile Model

User is the account/auth identity. Profiles are role-specific product identities connected to that user.

  • One user can have one or more profile types.
  • A user can have an Athlete Profile, a Professional Profile, or future profile types.
  • Profile-user relationships define which users are connected to each profile.
Future scaling plans: new profile types should plug into the same User/Profile relationship instead of requiring a new auth model.

Public vs Private Profiles

The athlete is the public showcase. Professionals work behind the scenes.

  • Athlete Profile is the public showcase profile in the MVP.
  • Professional / Scout Profile is private and not publicly searchable.
  • Athletes may see a limited scout card only after interaction.
Future scaling plans: professional public visibility can be considered later, but it is not part of the MVP platform posture.
Core platform split: athletes present themselves through public structured portfolios, while scouts work through private professional tools.

Consent And Verification Rule

Third-party consent and ID verification

Guardian consent, guardian ID verification, and adult athlete ID verification are handled through trusted third-party programs. The platform stores only the result, timestamp, provider reference, and accepted policy version.

Access And Workspace Decisions

The MVP keeps onboarding and workspaces simple while preserving the architecture needed for organizations later.

Signup And Access

Signup is free for everyone in the MVP.

  • Free signup does not automatically mean public visibility.
  • Product access and visibility can still depend on profile readiness and profile settings.
Future scaling plans: paid plans can be layered around advanced professional and organization features without changing free account creation.

Scout Workspace Model

MVP work happens inside individual scout workspaces.

  • Every scout gets an individual workspace.
  • Agency, club, or company affiliation can exist as lightweight project context.
  • Affiliation groups scouts structurally but does not create a separate MVP workflow.
Future scaling plans: organization workspaces can add team collaboration, roles, hierarchical permissions, reporting, and shared visibility as an advanced layer.

Cross-Cutting Preservation Principle

Nothing is permanently deleted unless the user deliberately chooses delete.

MVP Behavior

  • Archive / recover is the safe default.
  • Delete is separate, deliberate, and irreversible.
  • Saved athletes, project history, notes, evaluations, and archived projects remain available unless explicitly deleted.

Future Scaling Plans

The same preservation rule should support audit history, organization reporting, collaboration history, and future compliance needs.

Platform rule: archive and recover by default; permanently delete only after explicit user intent.
